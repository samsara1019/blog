팀에서 Claude Code를 쓴 지 1년이 안 된다. 그동안 규칙을 나눠 쓰는 방식이 세 번 바뀌었다.

| 단계 | 방식 | 규칙이 사는 곳 |
| --- | --- | --- |
| 1 | CLAUDE.md를 복사해서 붙여넣기 | 각자의 PC |
| 2 | 규칙 전용 레포 + 심볼릭 링크 | 레포 하나 |
| 3 | 사내 플러그인 | 마켓플레이스 |

이 글은 1단계와 2단계다. 2편은 2단계를 점검하다 알게 된 것, 3편은 플러그인 이야기다.

## 1단계: 복붙

처음에는 CLAUDE.md를 메신저로 주고받아 각자 붙여넣었다. 가장 빠른 방법이었고, 처음 며칠은 문제가 없었다.

문제는 규칙이 고쳐질 때 생겼다. 누군가 "타입 이름에는 `T` 접두사를 붙인다"를 추가해도 다른 사람의 파일에는 들어가지 않는다. 같은 코드베이스를 두고 Claude가 사람마다 다른 규칙으로 코드를 썼다. 리뷰에서 "이건 왜 이렇게 했어요?"라고 물으면 답은 "제 Claude는 그렇게 하던데요"였다.

복붙은 공유가 아니라 분기다. 붙여넣은 순간부터 사본은 따로 낡는다.

## 각 레포에 커밋하는 방법은 왜 안 했나

가장 흔한 방법은 CLAUDE.md를 각 레포에 커밋하는 것이다. Claude Code가 레포 루트의 CLAUDE.md를 자동으로 읽으니 링크도 설치도 필요 없다. 생각은 했지만 하지 않았다.

당시 프론트엔드 레포가 다섯 개였다([모노레포 1편](/blog/monorepo-1-iframe-to-import/)). 규칙 대부분은 다섯 레포에 똑같이 적용된다. 각 레포에 커밋하면 사본이 다섯 벌이 되고, 복붙과 같은 문제가 레포 단위로 다시 생긴다. 규칙 하나를 고치려면 PR이 다섯 개 필요하다.

## 2단계: 규칙 전용 레포

2026년 1월에 규칙만 담는 레포를 따로 만들었다. `team-claude`라고 부르겠다.

```
team-claude/
├── CLAUDE.md          # 팀 공통 규칙
└── .claude/
    ├── settings.json  # 훅 등록
    ├── commands/      # 슬래시 커맨드
    ├── hooks/         # 훅 스크립트
    ├── knowledge/     # 컨벤션 문서
    └── specs/         # 기능 스펙
```

이 레포를 코드 레포 다섯 개에 어떻게 연결하느냐가 문제였다. 답은 작업 폴더의 심볼릭 링크다.

```
workspace/                         # Claude Code를 여기서 연다
├── team-claude/
├── service-a/
├── service-b/
├── ...
├── .claude   -> team-claude/.claude
└── CLAUDE.md -> team-claude/CLAUDE.md
```

레포들을 한 폴더에 나란히 두고, 그 폴더에 `team-claude`를 가리키는 링크 두 개를 만든다. Claude Code는 현재 폴더와 상위 폴더의 CLAUDE.md와 `.claude/`를 읽으므로, 어느 레포를 고치든 같은 규칙이 붙는다.

```bash
cd workspace
ln -s team-claude/.claude .claude
ln -s team-claude/CLAUDE.md CLAUDE.md
```

좋은 점은 셋이다.

- **규칙이 한 곳에 있다.** 고치면 `git pull` 한 번으로 모두에게 간다
- **규칙 변경이 PR이 된다.** 누가 왜 바꿨는지 남고 리뷰를 받는다
- **코드 레포를 건드리지 않는다.** 규칙을 고칠 때 코드 레포에 커밋이 생기지 않는다

걸렸는지 확인하는 방법도 단순했다. 세션에서 팀 커맨드(`/spec-writer`)가 보이면 된 것이다.

## 레포에 쌓인 것

10개월 동안 커밋이 590개쯤 쌓였다. 처음에는 컨벤션 문서뿐이었다.

| 시기 | 추가된 것 |
| --- | --- |
| 1월 | 타입 이름 규칙, 상수 파일 구조, 함수 이름 규칙 |
| 1월 말 | `/commit`, `/feature` 커맨드, 스펙 템플릿 |
| 이후 | `/pr`, `/code-review`, 스펙 작성·검증 커맨드까지 12개 |
| | PreToolUse 훅 2개, push 전에 도는 비밀값 스캐너 |
| | 기능 스펙 약 150개 |

중간에 레포의 성격이 하나 더 생겼다. **스펙 저장소**다. 기능을 만들기 전에 스펙을 `specs/`에 쓰고, Claude가 그 스펙을 읽고 구현한다. 기획자가 스펙을 쓰고 QA가 스펙으로 테스트 케이스를 뽑는 흐름까지 커맨드로 넣었다.

스펙이 늘자 정리 규칙이 필요했다. 9월에 30여 개 폴더 131개 파일을 `{제품}/{기능}` 구조로 다시 나눴다. 기준은 "폴더는 코드의 위치를 따른다"다. 스펙을 찾는 사람은 어느 화면을 고치는지는 알지만 그 스펙이 어떤 분류였는지는 모른다.

## 2단계의 한계

이 구조로 9개월을 썼다. 몇 가지가 계속 걸렸다.

- **링크를 안 걸면 규칙이 없는 것과 같다.** 새 팀원이 레포만 clone하고 Claude를 열면 아무 규칙 없이 코드를 쓴다. 에러도 경고도 없다
- **CLAUDE.md가 계속 커진다.** 33KB를 넘었다. 모든 세션이 이 전부를 읽는다
- **백엔드 팀과 나눌 수 없다.** 백엔드도 비슷한 규칙과 도구가 필요했지만, 프론트엔드 작업 폴더에 묶인 구조라 같이 쓸 수 없었다
- **적어 둔 규칙이 정말 지켜지는지 아무도 몰랐다**

마지막 것이 가장 컸다. 9월에 레포 전체를 점검했다. 그 이야기가 2편이다.

## 기억할 점

- **복붙은 공유가 아니라 분기다.** 붙여넣은 순간부터 사본은 따로 낡는다
- **같은 규칙을 여러 레포가 쓰면 규칙을 레포 밖으로 뺀다.** 각 레포에 커밋하면 사본이 레포 수만큼 생긴다
- **상위 폴더의 심볼릭 링크는 가장 가벼운 공유 수단이다.** 코드 레포를 건드리지 않고 규칙 변경을 PR로 관리할 수 있다
- **다만 링크는 강제되지 않는다.** 걸지 않은 사람에게는 규칙이 없다
