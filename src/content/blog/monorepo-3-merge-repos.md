## 디렉터리 구조

```
front/
├── apps/                  # 배포 단위. 각자 nuxt.config.ts와 package.json
│   ├── service-a/
│   ├── service-b/
│   ├── service-c/         # 기존 코드 (이관 대기)
│   ├── service-c-new/     # 재구현. 모노레포 방식의 시범 사례
│   ├── service-d/
│   └── ui-docs/           # Storybook. 배포하지 않는다
├── packages/
│   ├── common-pages/      # 공유 페이지 컴포넌트. iframe을 대체한다
│   ├── composables/
│   ├── config/            # eslint, tsconfig 공용 설정
│   ├── types/
│   ├── ui/
│   └── utils/
├── docker/Dockerfile      # 공용 1개
├── turbo.json
└── pnpm-workspace.yaml
```

`apps/`는 배포 단위이고 `packages/`는 라이브러리다. 이 구분 하나만 지켜도 "이 코드는 어디에 두나"라는 질문의 절반이 풀린다.

## 1단계: 히스토리를 살려서 합치기

레포를 그냥 복사해 넣으면 커밋 히스토리가 사라진다. `git blame`이 전부 "모노레포로 이동"이라는 커밋 하나를 가리키게 된다.

`git filter-repo`로 각 레포의 모든 커밋을 하위 디렉터리로 옮긴 뒤 병합했다.

```bash
# 임시로 clone한 레포에서: 모든 커밋의 경로를 apps/service-a/ 아래로 다시 쓴다
git filter-repo --to-subdirectory-filter apps/service-a

# 모노레포에서: 관계없는 히스토리를 허용하고 병합한다
git remote add temp <임시 경로>
git fetch temp
git merge temp/main --allow-unrelated-histories -m "Merge service-a into apps/service-a"
```

레포 수만큼 반복하는 스크립트를 만들어 돌렸다.

알아둘 점이 있다.

- `filter-repo`는 히스토리를 다시 쓰므로 커밋 해시가 전부 바뀐다. 원본 레포의 해시로 적어 둔 링크는 더 이상 맞지 않는다
- 반드시 임시 clone에서 실행한다. 원본에서 돌리면 원본 히스토리가 바뀐다


## 2단계: 병행 개발 기간의 변경분 반영

합친 날 바로 기존 레포를 닫지 못했다. 운영 중인 서비스라 기존 레포에서 개발이 계속됐고, 모노레포는 그 변경을 따라가야 했다.

기존 레포의 변경분은 세 번 반영했다.

| 시점 | 방식 | 상황 |
| --- | --- | --- |
| 2026-02 | 커밋 370여 개를 squash | 모노레포는 아직 쓰이지 않았다. 기존 레포를 따라가기만 했다 |
| 2026-05-18 | `rsync --delete` 스냅샷, 커밋 480여 개 분량 | 이날부터 모노레포에서 개발을 시작했다 |
| 2026-06-16 | 커밋 단위 재생 | 기존 레포의 마지막 변경분 |

1월에 합치고 5월 중순까지 모노레포는 사실상 비어 있었다. 2월에 한 번 따라잡은 것 말고는 커밋이 없다. 모든 개발이 기존 레포에서 계속됐다.

양쪽에서 동시에 개발한 병행 기간은 5월 18일부터 6월 16일까지 한 달 정도다. 바로 전환하지 못한 이유는 두 가지다. 새 배포 파이프라인이 준비돼야 했고, 기존 개발자들이 새 구조를 익힐 시간이 필요했다. 앱 하나는 7월 초에 기존 레포와 한 번 더 맞췄다.

처음 두 번은 급하게 반영했다. 코드는 맞게 들어왔지만 그 구간의 히스토리가 커밋 하나로 뭉개졌다.

세 번째는 커밋 단위로 옮겼다.

```bash
# 기존 레포의 커밋을 패치로 뽑아, 하위 디렉터리에 그대로 재생한다
git am --3way --directory=apps/service-a <패치 파일>
```

`--directory`가 경로 앞에 접두사를 붙여 준다. 작성자와 날짜가 보존된다.

### 재생이 안 되는 커밋

단순 재생이 안 되는 것들이 있었다. 모노레포 쪽에서 이미 리팩터가 진행돼 구조가 달라진 경우다. 세 갈래로 처리했다.

| 처리 | 경우 |
| --- | --- |
| 그대로 재생 | 구조가 같은 변경 |
| 손으로 다시 구현 | 기능은 필요한데 대상 코드의 위치나 구조가 달라진 경우 |
| 의도적으로 건너뜀 | 모노레포가 같은 목적을 다른 방식으로 이미 달성한 경우 |

건너뛴 것은 이유를 문서에 남겼다. 나중에 "이 PR은 왜 모노레포에 없지"라는 질문이 반드시 나온다.

### 번역 키 충돌

예상하지 못한 것이 하나 있었다. 번역 키를 `apply.404`처럼 번호로 관리하는데, 병행 기간에 양쪽이 각자 번호를 늘려 갔다. 같은 번호가 기존 레포와 모노레포에서 서로 다른 문장을 가리키게 됐다.

코드는 충돌 없이 합쳐지는데 화면에는 엉뚱한 문구가 나온다. 이 부분은 자동으로 풀 수 없어서 새 번호를 다시 발급하고 코드를 고쳤다.

## 3단계: 뭉개진 히스토리 되살리기

squash와 스냅샷으로 뭉개진 두 구간이 아쉬웠다. 히스토리를 다시 쓰면 모든 해시가 바뀌고 열려 있는 PR이 전부 깨진다.

`git replace --graft`를 썼다. 히스토리를 다시 쓰지 않고, "이 커밋을 볼 때는 이 부모로 이어진 것처럼 보여 달라"는 매핑만 추가한다.

```bash
git replace --graft <squash 커밋> <원본 히스토리의 마지막 커밋>
```

팀원은 clone 직후 한 번만 실행하면 된다.

```bash
git fetch origin '+refs/replace/*:refs/replace/*'
```

`git clone`과 일반 `git fetch`는 `refs/heads/*`만 가져온다. `refs/replace/*`는 명시해야 온다. 작은따옴표를 빼면 셸이 `*`를 풀어 버린다.

확인은 이렇게 한다.

```bash
git replace -l                                    # 매핑 두 개가 보이면 적용됨
git --no-replace-objects log --oneline -- apps/service-a | wc -l   # 적용 전
git                          log --oneline -- apps/service-a | wc -l   # 적용 후
```

압축 구간의 커밋이 5개에서 460여 개로 늘어난다.

알아둘 점이 있다.

- 커밋 해시는 하나도 바뀌지 않는다. CI, 열린 PR, 다른 브랜치에 영향이 없다
- `git log`, `git blame`, `git show` 같은 CLI에만 적용된다. GitHub 웹 화면에는 squash 커밋이 그대로 보인다
- 실행하지 않아도 작업에는 지장이 없다. 압축된 모습으로 보일 뿐이다

## 4단계: 의존성 버전 맞추기

레포마다 따로 올리던 버전이 합치는 순간 충돌한다. 루트 `package.json`의 `pnpm.overrides`로 고정했다.

```json
{
  "pnpm": {
    "overrides": {
      "nuxt": "3.14.159",
      "@nuxt/kit": "3.14.159",
      "vite": "5.4.21"
    }
  }
}
```

프레임워크 버전은 범위(`^`)가 아니라 정확한 버전으로 박았다. 앱마다 Nuxt 패치 버전이 다르면 공유 패키지가 어느 쪽에서도 완전히 맞지 않는다.

저장소에서 확인한 사실은 이렇다.

- Vue 버전을 강제로 맞춘 적은 없다. 앱마다 `^3.3.x`, `^3.5.x`로 범위가 다르지만 lockfile이 하나라서 한 버전으로 풀린다
- 강제로 고정한 것은 Nuxt와 빌드 도구다

### overrides는 `package.json`의 범위를 이긴다

지금 앱의 `package.json`에는 `"nuxt": "^4.6.3"`이라고 적혀 있다. 실제로 설치된 것은 3.14.159다. 루트의 override가 각 워크스페이스의 범위보다 우선하기 때문이다.

```bash
pnpm why nuxt --filter service-a    # 실제로 설치된 버전과 이유를 보여준다
```

모노레포에서는 `package.json`만 보고 버전을 믿으면 안 된다.

범위를 올린 것은 사람이 아니다. 2026년 11월에 dependabot의 묶음 PR이 앱 네 개의 범위를 `^3`에서 `^4.6.3`으로 올렸다. override가 막고 있어서 설치 버전은 그대로이고 빌드도 통과한다. 이 글을 쓰면서 `package.json`과 설치 버전을 나란히 보다가 알았다.

겉으로는 아무 일도 없지만 위험한 상태다. 누군가 override를 지우는 순간 메이저가 한꺼번에 올라간다. 범위를 `^3`으로 되돌리고, dependabot이 프레임워크의 메이저를 올리지 못하게 `ignore` 규칙을 넣는 것이 맞다.

### 범위를 좁힌 override

테스트 러너만 다른 vite 메이저가 필요했다.

```json
{
  "pnpm": {
    "overrides": {
      "vite": "5.4.21",
      "vitest>vite": "7.2.4"
    }
  }
}
```

`부모>자식` 표기는 "이 패키지 아래에 설치되는 것만" 바꾼다. 앱 빌드는 vite 5를 쓰고 vitest는 vite 7을 쓴다.

워크스페이스 안의 패키지는 이렇게 가리킨다.

```json
{ "dependencies": { "@acme/utils": "workspace:*" } }
```

pnpm이 `node_modules/@acme/utils`를 `packages/utils`로 심볼릭 링크한다. 배포 없이 바로 import된다.

## 5단계: 무엇을 패키지로 뽑을 것인가

너무 많이 뽑으면 패키지가 늘어나고, 너무 안 뽑으면 중복이 남는다. 기준은 이랬다.

- 타입과 상수를 먼저 뽑는다
- 컴포넌트와 훅은 실제로 두 개 이상의 앱이 import할 때 옮긴다
- 도메인에 특화된 코드는 뽑지 않는다. 비즈니스 로직은 composable로 분리하되 앱 디렉터리에 둔다

공용 UI 컴포넌트를 뽑으면서 정한 규칙도 있다.

- 앱의 SCSS 변수에 의존하지 않는다. CSS 변수를 쓴다
- 아이콘 라이브러리를 직접 쓰지 않는다. slot으로 받아 앱이 원하는 아이콘을 넘기게 한다
- 번역을 모른다. 문구는 props로 받는다

규칙의 방향은 하나다. 공용 패키지가 앱의 사정을 알면 안 된다.

## 6단계: iframe을 한 번에 걷어내지 못한 이유

모노레포로 옮긴 직후에도 iframe은 그대로였다. common 레포는 `packages/common`으로 들어왔을 뿐 여전히 별도 Nuxt 앱이었다. 레포만 합친 상태로는 모노레포의 값을 못 낸다.

공유 페이지 하나를 골라 컴포넌트로 뽑아 보니 단순한 파일 이동이 아니었다.

```
공유 페이지
  ├── 입력 컴포넌트들
  │     ├── 폼 검증 스토어 (Pinia)
  │     ├── 전역 플러그인의 유틸 함수 (한 파일에 700줄 이상)
  │     └── 앱의 번역 키
  ├── composable
  ├── 앱마다 중복 정의된 axios 인스턴스
  └── 번역 키 64개
```

페이지를 옮기려면 그 아래 의존을 먼저 패키지로 뽑아야 했다. 아래에서 위로 단계를 나눴다.

| 단계 | 작업 | 이유 |
| --- | --- | --- |
| A | 비즈니스 로직을 composable로 추출 | 위험이 가장 낮다. iframe을 유지한 채 양쪽이 같은 로직을 쓴다 |
| B | 전역 플러그인의 유틸 함수를 utils 패키지로 | 플러그인 주입에서 import로 바꿔 결합을 낮춘다 |
| C | 폼 검증 스토어 이동 | 입력 컴포넌트를 옮기기 위한 조건 |
| D | 중복된 axios 설정을 하나로 | 다른 단계와 무관하게 진행할 수 있다 |
| E | 입력 컴포넌트를 ui 패키지로 | 페이지를 옮기기 직전 단계 |
| F | 공유 페이지를 common-pages 패키지로 | 아래 의존이 모두 패키지가 된 뒤 |
| G | 각 앱에서 iframe을 지우고 직접 import | 검증 후 화면별로 적용 |
| H | common 앱 종료 | 마지막 정리 |

단계 B에서 지킨 원칙이 있다. 유틸 함수 50여 개를 한 번에 옮기지 않고, 옮기려는 페이지가 실제로 쓰는 4~5개부터 옮겼다.

### 결과: 두 달 만에 다 걷어냈다

| 시점 | 일 |
| --- | --- |
| 2026-05-20 | 첫 공유 페이지를 패키지로 추출 |
| 2026-06-22 ~ 07-02 | 남은 iframe 화면을 차례로 컴포넌트로 전환 |
| 2026-07-15 | 공통 iframe 앱을 저장소에서 삭제 |

화면을 옮길 때마다 `postMessage`를 Vue의 `emit`으로 바꿨다. 25종 안팎의 메시지를 셋으로 나눴다.

| 분류 | 뜻 | 예 |
| --- | --- | --- |
| 소멸 | 경계가 없어져 필요 없어진 것 | iframe 높이 전달, 스크롤 동기화 |
| emit | 부모가 알아야 하는 사건 | 상세 화면 열기, 데이터 다시 불러오기 |
| 유지 | 여전히 창 사이 통신이 필요한 것 | 끝내고 보니 하나도 남지 않았다 |

"유지" 칸에 남은 것은 없다. 부모 창에 띄우던 토스트 알림까지 `emit`으로 바뀌었다. 공유 화면이 부모와 같은 문서에 렌더링되면 창 사이 통신이 필요한 일 자체가 없어진다.

```vue
<!-- 전: iframe과 메시지 리스너 -->
<iframe :src="commonUrl" />

<!-- 후: 컴포넌트와 이벤트 -->
<TaskFlow @refetch="refetch" />
```

숫자로 보면 이렇다.

| | 병합 시점 (2026-01) | 지금 |
| --- | --- | --- |
| `postMessage`와 메시지 리스너 코드 | 90개 파일 234줄 | 테스트를 빼면 2줄 |
| 공통 iframe 앱 | 소스 파일 약 280개 | 삭제 |

남은 2줄 중 하나는 다른 서비스의 화면을 띄우는 별개의 iframe이다. 다른 하나는 부모 창에 토스트를 보내던 유틸인데, 이제 부르는 곳이 없어서 지우면 된다.

## 기억할 점

- **히스토리는 합칠 때 살린다.** `git filter-repo --to-subdirectory-filter`로 경로만 옮겨 병합하면 `git blame`이 살아남는다
- **squash로 뭉갠 히스토리는 `git replace --graft`로 되살릴 수 있다.** 해시를 바꾸지 않아서 안전하지만 CLI에서만 보인다
- **병행 개발 기간을 짧게 잡는다.** 길어질수록 양쪽이 벌어지고, 재생할 수 없는 커밋이 늘어난다
- **번호로 관리하는 자원(번역 키, ID)은 병합 때 조용히 충돌한다.** git은 잡아 주지 않는다
- **건너뛴 변경은 이유를 적어 둔다**
- **레포를 합치는 것과 코드를 공유하는 것은 다른 일이다.** 합친 뒤에도 iframe은 그대로였다. 의존 그래프의 바닥부터 올라가야 한다
- **한 번에 다 옮기지 않는다.** 지금 옮기려는 화면이 쓰는 것만 옮긴다
- **overrides는 `package.json`의 범위를 이긴다.** 실제 버전은 `pnpm why`로 본다. 봇이 범위만 올려 두고 override가 막고 있는 상태는 조용한 시한폭탄이다
- **`postMessage`를 걷어낼 때는 먼저 분류한다.** 없어질 것, 이벤트가 될 것, 남을 것. 우리는 남을 것이 없었다
