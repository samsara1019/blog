9월에 규칙 레포(`team-claude`)에 무엇이 있고 그중 무엇이 실제로 동작하는지 전부 세어 봤다. 계기는 단순했다. 새 도구를 하나 더 붙이려다가, 이미 있는 것이 뭔지 설명을 못 하겠더라.

## 세어 본 결과

**실제로 동작하는 것**

| 항목 | 수 | 동작 방식 |
| --- | --- | --- |
| CLAUDE.md | 28KB | 세션마다 읽힌다 |
| PreToolUse 훅 | 2개 | Edit/Write 전에 금지 패턴 5개 차단, push 전에 diff에서 비밀값 검사 |
| push 전 스캐너 | 레포 5개에 설치 | git 훅이라 Claude를 안 써도 돈다 |
| 슬래시 커맨드 | 13개 | 사람이 부를 때 |
| 컨벤션 문서·스펙 | 약 150 파일 | 커맨드와 CLAUDE.md가 가리킨다 |

**문서로만 있는 것**

| 항목 | 수 |
| --- | --- |
| 에이전트 정의 yaml | 6 |
| 워크플로 yaml | 6 |
| 스킬 ts | 10 |
| 컨텍스트 md | 9 |

아래 표는 1월에 레포를 만들 때 "역할별 에이전트와 워크플로"를 설계하며 넣은 것이다. CrewAI 같은 멀티에이전트 프레임워크의 선언 형식이었는데, 그것을 실행할 런타임을 붙인 적이 없다. Claude Code는 이 형식을 읽지 않는다. 8개월 동안 아무도 쓰지 않았고 아무도 몰랐다.

CLAUDE.md 안에도 같은 것이 있었다. 하단의 "규칙 파일" 절과 예시로 적은 에이전트 이름이 실체가 없었다. 모델은 매 세션 그 문장을 읽었다.

## 틈 네 개

동작하는 것들에도 틈이 있었다.

**1. 금지 패턴 훅은 Bash로 우회된다.** 훅은 Edit와 Write만 본다. `sed -i`나 heredoc으로 파일을 쓰면 검사하지 않는다. 모델이 일부러 우회하는 것이 아니라, 파일을 고치는 방법이 여럿이고 훅이 그중 둘만 본 것이다.

**2. 스캐너가 심볼릭 링크를 전제한다.** 1편의 링크 구조를 전제로 만들어져서, 규칙 레포를 직접 열면 경고만 내고 통과시킨다.

**3. 개인 설정 파일이 커밋돼 있었다.** `.claude/settings.local.json`은 각자의 PC용 파일인데 처음에 커밋됐다. 그 뒤 `.gitignore`에 넣었지만 이미 추적 중인 파일에는 소용이 없다. 다른 사람의 홈 경로와 권한 설정이 모두에게 갔고, 모두의 `git status`에 "수정됨"이 두 달째 떠 있었다.

**4. 지시 층에만 있는 규칙은 강제되지 않는다.** CLAUDE.md에 `any` 금지라고 적는 것과 훅으로 막는 것은 다른 층이다. CLAUDE.md의 규칙 대부분은 전자였다.

## 다섯 층

세어 보고 나니 하네스를 한 덩어리로 보면 안 된다는 것이 분명해졌다. 층으로 나눴다.

| 층 | 역할 | 수단 |
| --- | --- | --- |
| 지시 | 규칙과 맥락을 프롬프트로 준다 | CLAUDE.md, 규칙 파일, 메모리 |
| 강제 | 어겨도 실행 단계에서 막는다 | PreToolUse 훅, 권한 allow/deny, git pre-commit/pre-push, CI |
| 절차 | 반복 작업을 재현 가능한 진입점으로 만든다 | 슬래시 커맨드, 스킬, 서브에이전트, 플러그인 |
| 연결 | 외부 도구와 데이터를 표준 인터페이스로 붙인다 | MCP 서버, CLI |
| 관측·검증 | 세션 로그, 결과 평가, 회귀 방지 | 텔레메트리 훅, eval, CI |

지시 층은 모델이 따르기를 **기대**하는 것이다. 강제 층은 어겨도 **통과하지 못하게** 하는 것이다. 이 구분이 전부다.

규칙 레포에는 지시 층과 절차 층이 두꺼웠고 강제 층이 얇았다. 문서로만 있던 yaml들은 어느 층에도 속하지 않았다.

## 무엇을 어느 층으로 옮기나

모든 규칙을 강제로 옮길 수는 없고 그럴 필요도 없다. 기준을 이렇게 잡았다.

- **어기면 되돌리기 비싼 것**은 강제로 옮긴다. 비밀값 커밋, 번역 파일 직접 수정, 금지된 API 호출
- **스타일과 취향**은 지시에 둔다. 어겨도 리뷰에서 잡으면 된다
- **강제 장치는 도구와 무관해야 한다.** Edit/Write 훅은 Bash를 못 본다. 커밋 단계(pre-commit)에서 같은 검사를 돌리면 어떤 도구로 고쳤든 걸린다

그리고 순서를 정했다. **죽어 있는 기존 장치를 살리는 것이 새 도구 도입보다 먼저다.** 당시 레포의 eslint가 설정 오류로 돌지 않고 있었다. AST 기반 규칙 검사기를 새로 붙이는 것보다 eslint를 살리는 것이 먼저였다.

## 게이트는 일부러 실패시켜 봐야 안다

이 점검에서 얻은 가장 큰 교훈은 따로 있다. "설치했다"와 "동작한다"는 다르다.

같은 달에 다른 레포에서 비슷한 일을 또 겪었다. push 전 보안 검사 훅을 `.git/hooks/`에 설치했는데 한 번도 실행되지 않았다. husky가 `core.hooksPath`를 바꿔 놓아서 git이 그 폴더를 보지 않았던 것이다. 이 이야기는 [모노레포 5편](/blog/monorepo-5-troubleshooting/)에 있다.

훅이든 테스트 단계든 게이트는 만든 직후에 일부러 위반을 넣어서 막히는지 본다. 막히지 않으면 없는 것이다.

## 기억할 점

- **지시는 기대, 강제는 차단.** CLAUDE.md에 적은 것은 모델이 따르기를 기대하는 것이지 보장이 아니다
- **하네스를 층으로 센다.** 무엇이 어느 층에 있는지 모르면 무엇이 동작하는지도 모른다
- **문서로만 있는 설정은 지운다.** 실행할 런타임이 없는 선언은 읽는 사람만 헷갈리게 한다
- **강제 장치는 도구와 무관한 자리에 둔다.** 파일을 고치는 방법은 훅이 보는 것보다 많다
- **죽은 장치 복구가 새 도구보다 먼저다**
- **게이트는 일부러 실패시켜 본다**
