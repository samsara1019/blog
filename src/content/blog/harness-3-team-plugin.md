2편의 점검 뒤 한 달 만에 구조를 바꿨다. 규칙 레포는 그대로 두고, 팀 전체가 공유할 것을 Claude Code 플러그인으로 뽑아 사내 마켓플레이스에 올렸다.

## 왜 플러그인인가

1편의 심볼릭 링크 구조에는 한계가 셋 있었다. 링크를 안 걸면 규칙이 없고, 백엔드 팀과 나눌 수 없고, 갱신이 각자의 `git pull`에 달려 있었다.

플러그인은 셋을 한 번에 푼다.

| 한계 | 플러그인에서 |
| --- | --- |
| 링크를 안 걸면 규칙이 없다 | 설치하면 어느 폴더에서 열어도 붙는다. 빠진 플러그인은 세션 시작 때 설치된다 |
| 백엔드와 나눌 수 없다 | 플러그인을 `core`·`be`·`fe` 셋으로 나누고 전원이 셋 다 설치한다 |
| 갱신이 각자 몫이다 | 세션 시작 때 원격 main과 비교해 새 버전을 받는다. **머지가 곧 배포, revert가 롤백** |

셋 다 설치하는 이유가 있다. 백엔드 개발자가 프론트 레포를 고칠 때도 프론트 규칙이 붙어야 하고, 어느 레포를 열었든 AWS 변경 같은 위험한 동작에는 같은 확인 창이 떠야 한다.

## 핵심 메커니즘: 고치기 직전에 규칙을 넣는다

CLAUDE.md는 세션 시작에 통째로 읽힌다. 33KB짜리 규칙을 매 세션 읽는 것은 비싸고, 읽은 지 오래된 규칙은 잊힌다.

플러그인은 다르게 했다. **파일을 만들거나 고치는 도구가 불리기 직전에**, 그 파일이 팀 저장소의 그 스택 코드이면 규칙 요약을 세션당 한 번 넣는다.

```
Edit/Write/Bash 호출
  └─ PreToolUse 훅
       ├─ 고치려는 파일이 팀 저장소 안인가?  (git origin + GitHub 팀 목록으로 판정)
       ├─ 어느 스택인가?                      (가장 가까운 package.json)
       └─ 이 세션에 아직 안 넣었으면 규칙 요약 주입
```

판정 기준에 폴더 이름을 쓰지 않는다. 사람마다 clone한 경로가 다르다. git origin과 GitHub 팀의 저장소 목록으로 재면 어디에 clone했든 같은 결과가 나온다. 팀에 저장소를 넣고 빼는 것이 곧 설정이다.

주입 자체는 수정을 막지 않는다. 요약은 그 수정과 함께 들어와 이후 작업에 적용되고, 위반은 금지 패턴 훅과 PR 전 리뷰 게이트가 잡는다.

규칙 요약에는 크기 한도가 있고 CI가 잰다. 2편에서 본 "CLAUDE.md가 계속 커진다" 문제를 숫자로 막는 장치다. 11월 한 달 동안 올라간 PR의 절반이 요약에서 문장을 **지우는** PR이었다. 코드를 읽으면 바로 알 수 있는 것, 일반 명령으로 알아낼 수 있는 것은 적지 않는다.

## 무엇을 플러그인에 넣고 무엇을 남기나

규칙 레포의 내용을 전부 옮기지 않았다. 기준 한 줄이 있었다.

> 티켓 작업 중에 같이 고쳐지는 것인가? 그렇다면 플러그인이 아니다.

| 플러그인에 넣는 것 | 규칙 레포에 남기는 것 |
| --- | --- |
| 팀이 실측으로 확인한 사실과 결정 | 코드와 함께 바뀌는 문서(스펙, API 문서) |
| 상대 팀이 알아야 할 규칙 요약 | 한 레포에서만 쓰는 도구 |
| 외부 시스템 지식과 도구 | 비밀값, 개인정보 |

그래서 규칙 레포는 없어지지 않았다. 스펙과 세부 컨벤션의 정본으로 남았고, 플러그인의 규칙 요약이 그것을 가리킨다. **같은 사실은 한 곳에만 둔다.** 사본은 따로 고쳐지다 어긋난다. 1편의 복붙에서 배운 것이 여기서도 기준이다.

하나 더. **값이 아니라 재는 법을 적는다.** 인프라 개수, 버전, 저장소 목록처럼 다시 알 수 있는 것은 그 값이 아니라 그것을 재는 명령을 적는다. 적어 둔 값은 바깥이 바뀌어도 그대로 남아 낡는다.

## 사고 하나가 가드 셋을 만들었다

10월 말에 사고가 났다. 환경 변수를 받아오는 스크립트를 Claude Code의 `!` 명령으로 실행하라고 안내했는데, 스크립트가 "터미널이 아니면 stdout으로 출력"하도록 돼 있었다. `!` 실행은 터미널이 아니다. dev 환경의 비밀값 네 개가 대화에 그대로 찍혔다.

대화에 들어간 값은 지울 수 없다. 로컬 기록과 모델 API 양쪽에 남는다. 복구는 키 교체뿐이었다.

이 사고로 세 가지가 바뀌었다.

1. **스크립트**에 TTY와 무관하게 파일에만 쓰는 모드를 넣었다. 화면에는 키 이름과 개수만 나온다
2. **운영 규칙**: 비밀값을 출력할 수 있는 스크립트는 Claude가 직접 실행하지도 `!`로 안내하지도 않는다
3. **가드 훅** 셋을 제안했다. 번역 파일 직접 수정 차단(`i18n-guard`), `.env`류 읽기와 `printenv` 차단(`env-guard`), push 전 비밀값 검사(`secret-guard`)

2편의 말로 하면, 사고가 "지시에 있던 규칙"을 "강제"로 옮기게 했다.

## 만들었다가 뺀 가드

셋 중 하나만 머지됐다. 이 부분이 이 글에서 가장 쓸모 있는 대목이다.

`i18n-guard`는 머지됐다. 번역 파일은 외부 시트가 정본이고 직접 고치면 다음 동기화 때 덮인다. 명확한 규칙이고, Edit/Write뿐 아니라 `sed -i`, `>`, `tee`, `cp`, python 쓰기까지 막는다. 2편의 "Bash 우회" 교훈을 반영했다.

`env-guard`는 **리뷰에서 빠졌다.** 리뷰어가 실험을 했다. 가짜 비밀값을 넣은 임시 프로젝트에서 평소 하는 요청 네 가지(DB 접속 실패, 외부 API 401, `.env` 점검, 설정 yaml 수정)를 두 번씩 돌렸다. 여덟 번 모두 `.env` 값이 대화에 나오지 않았다. 모델이 키 이름만 뽑거나 값을 가리고 길이만 비교하는 식으로 알아서 처리했다. 같은 호출 45개를 가드에 돌려 보니 거부 18건 중 11건은 값이 출력되지 않는 명령이었다. 오탐이 정탐보다 많았다.

`secret-guard`는 따로 떼어 다시 올렸고, 리뷰에서 테스트용 환경 변수가 검사를 통째로 건너뛰는 우회 경로가 된다는 지적을 받았다. 아직 머지되지 않았다.

여기서 배운 것이 둘이다.

- **가드를 만들기 전에 모델이 이미 하고 있는지 잰다.** 사고 직후에는 모든 것을 막고 싶다. 하지만 막는 것에도 비용이 있다. 오탐마다 사람이 멈춘다
- **우회 표식은 두지 않고, 오탐을 피하려고 차단을 경고로 낮추지도 않는다.** 우회가 있으면 게이트가 있으나 마나다. 오탐이면 판정을 고치는 PR을 낸다. 테스트 편의로 넣은 환경 변수도 우회 경로다

## 게이트를 비켜 가는 실행은 사람이 한다

플러그인 레포의 원칙 중 하나를 그대로 옮긴다.

> 게이트를 비켜 가는 실행(`--admin`, `--no-verify`, 플러그인 끄기)은 사용자가 요청해도 AI가 하지 않고 사람이 직접 한다. AI는 사용자 계정 토큰으로 일해 GitHub가 사람과 구분하지 못하고, 승인 게이트는 사람이 보는 마지막 장치다.

Claude Code는 내 토큰으로 push하고 PR을 만든다. GitHub 입장에서는 내가 한 일이다. `--no-verify`를 AI가 붙이기 시작하면 게이트는 사람이 보는 장치가 아니게 된다. 그래서 우회는 AI에게 시키지 않는 것으로 못 박았다.

## 기억할 점

- **규칙은 읽을 때가 아니라 쓸 때 넣는다.** 세션 시작에 전부 읽히는 CLAUDE.md보다 고치기 직전에 들어오는 요약이 싸고 잊히지 않는다
- **판정은 폴더 이름이 아니라 git origin으로.** 사람마다 경로가 다르다
- **머지가 곧 배포인 구조를 만든다.** 각자의 `git pull`에 맡기면 규칙 버전이 사람마다 달라진다
- **가드를 만들기 전에 모델이 이미 하고 있는지 잰다.** 사고 직후의 가드 요청은 절반이 불필요하다
- **우회 표식을 두지 않는다.** 편의로 넣은 환경 변수 하나가 게이트를 없앤다
- **지우는 PR이 늘어나면 잘 가고 있는 것이다.** 규칙은 쌓이는 것보다 줄어드는 것이 어렵다
