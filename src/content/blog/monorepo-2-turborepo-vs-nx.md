## 후보

| 도구 | 성격 |
| --- | --- |
| pnpm workspaces 단독 | 패키지 매니저 수준. 캐싱 없음 |
| pnpm + Turborepo | 캐싱과 태스크 실행 순서 관리 |
| Nx | 모노레포를 플랫폼으로 운영하는 도구 |

Lerna, Rush, Bazel은 규모가 맞지 않아 일찍 제외했다.

## 비교

| 항목 | pnpm 단독 | pnpm + Turborepo | Nx |
| --- | --- | --- | --- |
| 러닝커브 | 매우 낮음 | 낮음 | 중간~높음 |
| 빌드 캐싱 | 없음 | 로컬 + 원격 | 로컬 + Nx Cloud |
| 원격 캐시 자체 호스팅 | 해당 없음 | 가능 (캐시 서버 필요) | 가능 (20.8부터, 공개 명세를 따르는 캐시 서버 필요) |
| 바뀐 것만 빌드 | 없음 | `--filter='[main]'` | `nx affected` (더 정밀) |
| 분산 실행 | 없음 | 없음 | Nx Agents |
| 코드 생성기 | 없음 | 없음 | generators |
| 의존 그래프 시각화 | 없음 | 제한적 | `nx graph` |
| 기존 구조 변경 | 없음 | `turbo.json` 하나 | `project.json` 다수 |
| 걷어내는 비용 | 없음 | 매우 낮음 | 높음 |

**2026-11에 다시 확인한 내용.** 도구를 고르던 때에는 "Nx의 원격 캐시 자체 호스팅은 유료"가 근거 중 하나였다. 지금은 사정이 다르다.

- Nx도 20.8부터 OpenAPI 명세를 따르는 캐시 서버를 직접 만들어 붙일 수 있다. `NX_SELF_HOSTED_REMOTE_CACHE_SERVER` 환경변수로 가리킨다
- 공식 S3 플러그인(`@nx/s3-cache`)은 쓰지 않는 편이 낫다. nx.dev의 공지에 따르면 이 플러그인을 포함한 자체 호스팅 캐시 패키지들은 2026-05-21부로 지원이 중단됐다. 고칠 수 없는 설계 결함(CVE-2025-36852)이 이유다. Nx가 권하는 길은 Nx Cloud를 쓰거나 위 명세대로 캐시 서버를 직접 두는 것이다
- Powerpack은 더 이상 단독 상품으로 팔지 않는다

결국 지금은 두 도구 모두 "캐시 서버를 직접 띄우면 무료"다. 이 항목은 더 이상 Turborepo를 고른 근거가 되지 못한다. 당시에는 근거였다고만 적어 둔다. 비교 글에서 가격과 정책은 가장 빨리 낡는다.

## 결정 근거 세 가지

**도구의 무게가 문제의 무게와 맞아야 한다.** Nx의 강점은 코드 생성기, 그래프 시각화, 분산 실행이다. 앱과 라이브러리가 수십 개를 넘고 서로 얽혀 있을 때 값을 한다. 우리는 앱 6개에 패키지 몇 개였다.

**기존 구조를 건드리지 않아도 됐다.** Turborepo는 루트에 `turbo.json` 하나를 추가하고 각 앱의 `package.json` 스크립트는 그대로 둔다. 번역 파일 동기화 같은 기존 운영 규칙도 그대로였다.

**되돌리는 비용이 낮다.** Turborepo를 걷어내는 일은 파일 하나와 의존성 하나를 지우는 일이다. Nx를 걷어내는 일은 리팩터에 가깝다.

## "Nx 캐시가 더 정밀하다"는 반론

맞는 말이다. Nx는 TypeScript import 그래프를 분석해서 "이 파일이 바뀌었지만 이 앱은 import하지 않으니 캐시를 유지한다"는 판단을 한다.

그 정밀함이 의미가 있으려면 앱끼리 의존이 복잡해야 한다. 우리 의존 그래프는 이렇다.

```
apps/service-a ──► @acme/common-pages ──► @acme/{composables, ui, utils}
apps/service-b ──► @acme/common-pages
apps/service-c ──► @acme/{utils, types, ui, composables, config}
apps/service-d ──► (없음)
```

앱끼리는 서로 import하지 않는다. 영향받는 앱은 거의 항상 "전부" 아니면 "하나"다. 캐시 무효화가 거칠어도 결과가 같다. 이론상의 정밀도가 실제 빌드 시간으로 이어지지 않으면 의미가 없다.

## Nx의 기능을 우리 상황에 대 보면

| 기능 | 값을 하는 조건 | 우리 |
| --- | --- | --- |
| `nx graph` | 패키지 20~50개 이상 | `package.json`을 보면 끝난다 |
| `nx affected` | 의존 그래프가 성기고 복잡할 때 | 결과가 "전부" 아니면 "하나" |
| Nx Agents | 단일 앱 빌드가 10분 이상 | 병렬 빌드에서 가장 긴 앱만 기다리면 된다 |
| generators | 앱이 분기마다 늘어날 때 | 앱 구성이 거의 고정 |

## Vercel에 묶이는 것 아닌가

아니다. Turborepo는 MIT 라이선스이고 원격 캐시 프로토콜이 공개돼 있다. Vercel 계정 없이 캐시 서버를 직접 둘 수 있다.

"자체 호스팅"이 무엇을 뜻하는지는 정확히 알아야 한다. Turbo는 S3 같은 저장소에 직접 붙지 않는다. Turbo가 말을 거는 상대는 HTTP 캐시 서버이고, 그 서버가 뒤에서 S3에 저장한다.

```
turbo  ──HTTP──►  캐시 서버  ──►  S3
                  (예: ducktors/turborepo-remote-cache)
```

Turbo 쪽에는 환경변수 세 개를 준다.

| 변수 | 뜻 |
| --- | --- |
| `TURBO_API` | 캐시 서버 주소 |
| `TURBO_TEAM` | 팀 이름. 캐시를 나누는 단위 |
| `TURBO_TOKEN` | 인증 토큰 |

**이 글을 쓰면서 알게 된 것.** 팀 문서에는 "S3 원격 캐시를 쓴다"고 적혀 있었다. 설정을 다시 읽어 보니 캐시 서버도 위 환경변수도 없었다. 원격 캐시는 연결된 적이 없었다. 자세한 내용은 5편 6번에 쓴다.

## 언제 Nx를 다시 볼 것인가

기준을 미리 적어 두었다. 셋 중 하나에 닿으면 다시 검토한다.

- 서로 의존하는 공통 라이브러리가 5개를 넘을 때
- 단일 앱 빌드가 10분을 넘을 때
- 새 앱을 한 달에 한 번 이상 만들게 될 때

첫 번째 기준에 "서로 의존하는"을 붙인 이유가 있다. 지금 패키지는 6개지만 의존은 한 층뿐이다. 공유 페이지 패키지가 composables, ui, utils를 쓰고, 나머지는 서로를 모른다. Nx의 정밀한 캐시가 값을 하는 조건은 패키지의 수가 아니라 의존 그래프의 깊이다.

## 기억할 점

- **도구를 고를 때 "더 좋은 것"이 아니라 "지금 문제에 맞는 것"을 고른다.** Nx가 나쁜 도구가 아니라 우리 문제보다 큰 도구였다
- **걷어내는 비용이 낮은 쪽부터 시도한다.** 틀렸을 때 싸게 틀린다
- **갈아탈 조건을 결정할 때 함께 적어 둔다.** 나중에 "왜 아직 이걸 쓰지"라는 질문에 답할 근거가 된다
- **Turbo는 캐시와 실행 순서를 맡는 도구다.** 변경 감지까지 해 준다고 기대하면 4편의 혼란을 겪는다
