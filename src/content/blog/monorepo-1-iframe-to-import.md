## 레포 5개

프론트엔드 레포가 5개였다. 모두 Nuxt 3 앱이다.

| 레포 | 역할 |
| --- | --- |
| service-a | 고객이 직접 쓰는 신청 서비스 |
| service-b | 내부 담당자가 쓰는 운영 툴 |
| common | service-a와 service-b가 함께 쓰는 화면 |
| service-c | 검색 서비스 |
| service-d | 개인 페이지 서비스 |

## common이 생긴 이유

service-a와 service-b는 사용자가 다르지만 거의 같은 화면이 여럿 있었다. 신청 폼, 조회, 입력 폼, 계산기 같은 것들이다.

양쪽에 따로 만들면 고칠 때마다 두 곳을 똑같이 고쳐야 한다. 한쪽을 빼먹는 일이 잦았고, 번역 키와 컴포넌트 스타일도 두 벌이 됐다. 그래서 공통 화면을 한곳에 두기로 했다.

## 그런데 왜 iframe이었나

멀티 레포에서는 다른 레포의 컴포넌트를 빌드 시점에 가져다 쓰기가 어렵다.

- npm에 배포하지 않으면 다른 레포에서 import할 수 없다
- 사설 레지스트리를 운영해야 한다
- 컴포넌트 패키지의 버전 관리가 일이 된다

가장 빠른 길은 common을 별도 Nuxt 앱으로 띄우고 두 앱에서 `<iframe>`으로 넣는 것이었다.

```
service-a (3000)                    service-b (3001)
   │                                     │
   │   <iframe src="http://localhost:3002/apply/..." />
   │                                     │
   └──────────►  common (3002, 독립 Nuxt 앱)  ◄──────────┘
```

당시로서는 합리적인 선택이었다. 레포 구조를 그대로 두고 화면을 한 벌로 만들 수 있었다.

## iframe이 만든 문제

| 항목 | 문제 |
| --- | --- |
| 타입 | 다른 origin을 런타임에 불러오므로 타입을 공유할 수 없다. props가 `postMessage`로 넘어가 IDE가 추적하지 못한다 |
| SSR | iframe 안쪽은 부모의 SSR과 별개라 첫 화면이 늦다 |
| HMR | 양쪽이 따로 갱신된다 |
| 인증 | origin이 달라 토큰과 쿠키를 넘기는 작업이 따로 필요하다 |
| 뒤로가기 | iframe 안의 이동이 부모의 history에 쌓이지 않는다. 뒤로가기를 누르면 부모 페이지가 통째로 뒤로 간다 |
| 운영 | 컨테이너, Dockerfile, 배포 파이프라인이 하나씩 더 있다 |

매일 부딪힌 것은 두 가지였다.

**스크롤.** iframe 안의 스크롤은 부모 스크롤과 분리된다. 페이지 길이가 바뀌면 자식이 자기 높이를 `postMessage`로 보내고 부모가 iframe 높이를 다시 맞춰야 한다. "제출 후 맨 위로", "에러 위치로 이동" 같은 동작도 부모와 자식이 합을 맞춰야 했다. 한쪽이 어긋나면 사용자는 잘린 화면이나 빈 공간을 본다.

**모달.** iframe 안에서 띄운 모달은 iframe 영역 안에 갇힌다. 화면 중앙에 오지 못하고, 배경 어둡게 처리도 iframe 안에만 깔린다. 스크롤 잠금은 부모와 자식을 각각 처리해야 했다. 확인 모달, 토스트, 사이드 패널처럼 "위에 떠야" 자연스러운 것들이 전부 여기에 걸렸다.

### 버튼 하나의 동작을 바꾸는 데 걸린 시간

가장 크게 데인 일은 중요한 버튼(CTA) 하나의 동작을 바꾸는 작업이었다. 버튼은 iframe 안의 common에 있고, 눌렀을 때 일어나는 일(페이지 이동, 데이터 다시 불러오기)은 부모 앱에 있다. 동작 하나를 바꾸려면 보내는 쪽과 받는 쪽을 모두 고쳐야 했다.

```ts
// common (iframe 안): 버튼을 누르면 부모에게 알린다
window.parent.postMessage({ type: 'OPEN_DETAIL', id }, parentOrigin);

// service-a와 service-b (부모): 각자 받아서 처리한다
window.addEventListener('message', (event) => {
  if (event.origin !== commonOrigin) return;
  if (event.data.type === 'OPEN_DETAIL') {
    router.push(`/detail/${event.data.id}`);
  }
});
```

단순화한 예다. 이런 메시지가 25종 안팎이었고, 병합 시점에 `postMessage`와 메시지 리스너 코드가 90개 파일에 234줄 있었다.

이 구조에서 실제로 낸 버그들이 git 이력에 남아 있다.

- **데이터 모양이 어긋난다.** 메시지 객체 안에 같은 이름의 키가 두 번 들어가, 로그인이 필요한지 알리는 값이 부모에게 전달되지 않았다. 타입 검사가 닿지 않는 자리라 실행해 봐야 안다
- **순서가 어긋난다.** 부모가 `message` 리스너를 등록하는 시점과 자식이 사용자 정보를 요청하는 시점을 맞추는 수정이 따로 필요했다
- **메시지 하나에 뜻이 여러 개 실린다.** 경로 변경 메시지 하나로 "뒤로 가기"와 "신청서 만들기"를 함께 처리하다가, 결국 메시지를 둘로 쪼갰다
- **같은 수정을 레포 세 곳에 올린다.** iframe 높이 계산을 고친 날에는 common과 부모 앱 두 곳에 같은 제목의 커밋이 하나씩 있다

버튼 하나를 고치는 일이 레포 세 곳의 수정과 배포가 됐다. 그래서 오래 걸렸다.

## 그래서 모노레포

한 줄로 줄이면 이렇다. iframe에서 벗어나, 빌드 시점에 결합되는 컴포넌트 재사용 구조를 갖추려고 옮겼다.

공유 화면이 부모 앱의 DOM에 직접 렌더링되는 컴포넌트가 되면 스크롤, 모달 z-index, 스크롤 잠금, 뒤로가기가 한곳에서 동작한다. 이것 하나만으로도 옮길 가치가 있었다.

함께 풀리는 것들도 있다.

| 문제 | 모노레포에서 |
| --- | --- |
| 복붙으로 관리되던 유틸·타입 | 패키지로 뽑고 `import` 한 줄 |
| 레포마다 다른 의존성 버전 | lockfile 하나, `overrides`도 한곳 |
| 레포마다 다른 lint·tsconfig | 설정 패키지를 모든 워크스페이스가 extends |
| 앱마다 따로인 빌드 스크립트 | 공용 Dockerfile 하나 |

## 뼈대에서 병합까지 넉 달

빈 모노레포 뼈대는 2025년 9월에 만들었다. 실제로 레포를 합친 것은 2026년 1월이다. 그 사이에 한 일은 설득이었다.

모노레포 전환은 사용자에게 보이는 것이 하나도 없는 작업이라 우선순위에서 계속 밀렸다. 따로 기간을 받지 못했고, 우선순위가 높은 기능을 개발하면서 틈틈이 진행했다.

## 감수한 것

모노레포가 공짜는 아니다. 미리 적어 두고 결정했다.

| 비용 | 완화책 |
| --- | --- |
| 레포가 커진다 | shallow clone을 안내한다 |
| 모두가 한 레포에서 일해 PR 충돌이 늘 수 있다 | 앱별로 건드리는 파일이 나뉘어 있어 실제 충돌은 드물다 |
| 새 팀원이 배울 것이 늘어난다 | 온보딩 문서를 쓴다 |
| 기본이 "전부 빌드"라 CI가 느려질 수 있다 | 범위 빌드와 캐시 (4편) |
| 레포 단위로 권한을 나눌 수 없다 | CODEOWNERS |

## 기억할 점

- **iframe은 "레포를 안 건드리고 화면을 공유하는" 가장 빠른 방법이지만, 비용은 경계에서 나온다.** 스크롤, 모달, 히스토리, 인증처럼 문서 하나를 전제로 한 것들이 전부 두 벌이 된다
- **모노레포의 본질은 "import 한 줄로 공유"다.** 캐시와 빌드 도구는 그 뒤에 따라오는 문제다
- **당시의 선택을 깎아내리지 않는다.** 제약이 달랐고, 제약이 바뀌어서 선택을 바꿨다
- **iframe 자체가 나쁜 것은 아니다.** 이후 외부 사이트에 우리 화면을 넣는 용도로는 iframe 전용 라우트를 새로 만들었다. 문제는 같은 팀의 코드를 공유하는 수단으로 쓴 것이었다
